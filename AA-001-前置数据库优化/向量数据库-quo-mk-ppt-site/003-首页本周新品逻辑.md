## 八、潜在问题分析

### 8.1 编辑精选问题

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| ⚠️ RANDOM() 性能问题 | 中 | 大数据量下全表扫描，性能差 |
| ⚠️ 无真正"精选"逻辑 | 高 | 只是随机选取，无质量/热度筛选 |
| ⚠️ 缺少软删除过滤 | 高 | 没有 `deleted_at IS NULL` 条件 |
| ⚠️ 无缓存机制 | 中 | 每次请求都查询数据库 |

### 8.2 本周新品问题

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| ⚠️ 名不副实 | 高 | "本周新品"实际是"最新上传"，无时间限制 |
| ⚠️ 缺少状态过滤 | 中 | 没有 `status = 'published'` 条件 |
| ⚠️ 可能返回草稿 | 中 | draft/archived 状态的记录也会返回 |

### 8.3 共同问题

| 问题 | 说明 |
|------|------|
| 配置硬编码 | 数量限制、排序方式等硬编码在组件中 |
| 无错误重试 | API 失败时无重试机制 |
| 无加载状态 | 初始加载时无骨架屏 |

## 九、改进建议

### 9.1 编辑精选优化

#### 方案1: 添加 is_featured 字段

```sql
-- 数据库层
ALTER TABLE ppt ADD COLUMN is_featured BOOLEAN DEFAULT FALSE;
CREATE INDEX ppt_featured_idx ON ppt (is_featured) WHERE is_featured = TRUE;

-- 查询优化
SELECT * FROM ppt 
WHERE is_featured = TRUE 
  AND status = 'published' 
  AND deleted_at IS NULL
ORDER BY RANDOM() 
LIMIT 8;
```

#### 方案2: 基于热度的伪随机

```sql
SELECT * FROM ppt 
WHERE status = 'published' 
  AND deleted_at IS NULL
ORDER BY (download_count + view_count) * RANDOM() DESC
LIMIT 8;
```

#### 方案3: 修复当前 API


### 9.2 本周新品优化

#### 方案1: 真正的"本周"过滤

```typescript
// 新建 /api/ppts/new-arrivals/route.ts
const oneWeekAgo = new Date();
oneWeekAgo.setDate(oneWeekAgo.getDate() - 7);
```

## 十二、总结

### 核心数据流

```
首页加载 → 并行请求两个 API → 数据库查询 → transform 转换 → 渲染卡片
```

### 关键映射关系

```
编辑精选: deleted_at IS NULL + downloads DESC → 8 条（未传 status，依赖排序）
本周新品: deleted_at IS NULL + created_at DESC → 12 条（未传 status，名为“本周”但无时间过滤）
```

### 数据完整性

- ⚠️ 首页请求未传 status=published，可能包含 draft/archived
- ⚠️ “本周新品”无时间窗口，仅按创建时间排序
- ✅ 软删除过滤在 `getPPTs` 中存在（deleted_at IS NULL）
- ⚠️ 数据量统计需实时更新（当前总量 1471，embedding 全量）

### 性能状况

- ✅ 有基础索引支持（created_at/download_count/status_created 复合）
- ⚠️ 无缓存/预热，全部实时查询
