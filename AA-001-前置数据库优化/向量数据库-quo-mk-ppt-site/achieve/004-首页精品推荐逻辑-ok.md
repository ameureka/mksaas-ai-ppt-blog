## 六、优缺点分析

### 6.1 优点
| 优点 | 说明 |
|------|------|
| ✅ 实现简单 | 代码量少，易于理解 |
| ✅ 每次刷新不同 | RANDOM() 保证内容多样性 |
| ✅ 无缓存问题 | 实时查询，数据始终最新 |

### 6.2 潜在问题（基于现实现）
| 问题 | 严重程度 | 说明 |
|------|----------|------|
| ⚠️ 无精选标记/人工控制 | 中 | 仅按下载量排序，无运营干预 |
| ⚠️ 未传 status=published | 中 | 可能包含 draft/archived |
| ⚠️ 无缓存 | 中 | 每次请求都查数据库 |
| ⚠️ SELECT * | 低 | SQL 分支返回全列（含 embedding 等） |
| ⚠️ 向量分支可能返回 meta | 低 | 仅 search 时生效，与精选无关 |

### 6.3 备注
- 软删除过滤：`getPPTs` 已包含 deleted_at IS NULL
- 状态过滤：首页请求未传 status，若需要仅展示发布内容，应在请求中添加
- 随机实现：`/api/ppts/featured` 的随机逻辑未在首页使用，如保留需补软删除/状态过滤

  .where(and(
    eq(ppt.status, 'published'),

  // 用热门内容补充

    .select()
    .from(ppt)
    .where(and(
      eq(ppt.status, 'published'),
      isNull(ppt.deletedAt),
      notInArray(ppt.id, featured.map(f => f.id))

    .orderBy(desc(ppt.downloadCount))
    .limit(limit - featured.length);

## 九、总结

### 当前状态
- 首页精选实际为“下载量排序 TOP 8”，通过 `/api/ppts` SQL 分支获取；未传 status，含 deleted_at 过滤。
- `/api/ppts/featured` 仍存在随机实现，但首页未使用。

### 核心问题
1. ⚠️ 未传 status=published，可能包含 draft/archived
2. ⚠️ 无精选标记/人工控制，仅按下载量排序
3. ⚠️ 无缓存/预热，实时查库
4. ⚠️ 返回全字段（含 embedding），有冗余
5. ⚠️ 随机端点未过滤软删除/状态（但未被首页使用）

### 建议优先级
1. **请求层**：精选/新品调用加 `status=published`；如需“精选”逻辑可增 is_featured 或质量门槛
2. **端点治理**：随机 `/api/ppts/featured` 若保留需补 deleted_at/status 过滤，或标记废弃
3. **数据裁剪**：精选响应可只返回卡片所需字段，减少冗余
4. **配置集中**：数量、排序、广告位集中到 config，便于调整
