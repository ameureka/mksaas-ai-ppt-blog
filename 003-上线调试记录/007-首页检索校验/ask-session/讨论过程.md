| 问题 | 描述 | 影响 |

| 3. 搜索范围有限 | 只搜索 title、author、tags | 不搜索 description，漏掉大量相关内容 |
| 4. 无相关性排序 | 结果按时间/下载量排序 | 最相关的结果可能排在后面 |

  const query = searchParams.get('q');

  // 1. 生成查询向量
  const queryEmbedding = await generateEmbedding(query);

  // 2. 向量相似度搜索
  const results = await db.execute(sql`
    SELECT *, 1 - (embedding <=> ${queryEmbedding}) as similarity
    FROM ppt
    WHERE deleted_at IS NULL
    ORDER BY embedding <=> ${queryEmbedding}
    LIMIT 20
  `);

  return Response.json({ results });

### 关系类型

| 方案 | 关系 | 说明 |
|------|------|------|
| 方案 A: 同库同表 | 1:1 字段 | 向量作为 ppt 表的一个字段（pgvector） |
| 方案 B: 同库分表 | 1:1 外键 | 单独的 ppt_embeddings 表，通过 ppt_id 关联 |
| 方案 C: 独立向量库 | 1:1 ID 映射 | 使用 Pinecone/Qdrant 等，通过 ID 关联 |

### 方案 A（推荐）：同库同表

sql
-- ppt 表直接存储向量
CREATE TABLE ppt (
  id TEXT PRIMARY KEY,
  title TEXT,
  description TEXT,
  tags TEXT[],
  -- ... 其他业务字段

  embedding vector(1536)  -- 向量字段，与业务数据同行
);

-- 搜索时一次查询搞定
SELECT id, title, description
FROM ppt
WHERE deleted_at IS NULL
ORDER BY embedding <=> $query_vector  -- 向量相似度排序
LIMIT 20;


优点: 简单、无需 JOIN、事务一致性好
缺点: 表变大、向量更新影响主表

### 方案 B：同库分表

sql
-- 主表
CREATE TABLE ppt (
  id TEXT PRIMARY KEY,
  title TEXT,
  -- 业务字段...
);

-- 向量表
CREATE TABLE ppt_embedding (
  ppt_id TEXT PRIMARY KEY REFERENCES ppt(id),
  embedding vector(1536),
  model TEXT,  -- 'text-embedding-3-small'
  updated_at TIMESTAMP
);

-- 搜索需要 JOIN
SELECT p.id, p.title
FROM ppt_embedding e
JOIN ppt p ON p.id = e.ppt_id
ORDER BY e.embedding <=> $query_vector
LIMIT 20;


优点: 主表轻量、向量可独立更新
缺点: 需要 JOIN

### 方案 C：独立向量库

PostgreSQL                     Pinecone/Qdrant
┌──────────────┐              ┌──────────────┐
│ ppt          │              │ vectors      │
│ id: ppt_001  │◄────────────►│ id: ppt_001  │
│ title: ...   │   ID 映射    │ values: [...]│
└──────────────┘              └──────────────┘

搜索流程:
1. 查询 Pinecone → 返回 [ppt_001, ppt_003, ppt_007]
2. 查询 PostgreSQL WHERE id IN (...) → 返回完整数据


优点: 专业向量库性能更好、可扩展
缺点: 复杂、需同步、额外成本

### 什么时候需要 Redis？

| 场景 | 当前状态 | 何时需要 |
|------|----------|----------|
| 高并发 API 限流 | 无限流 | 日活 > 1万 或 AI API 成本控制 |
| 热数据缓存 | 无缓存 | 数据库查询成为瓶颈时 |
| 实时功能 | 无 | 需要 WebSocket/实时通知时 |
| 分布式锁 | 无 | 多实例部署防并发冲突时 |
